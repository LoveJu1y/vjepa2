# EK100 任务中的 V-JEPA2 额外训练头（按数据流逻辑讲清楚）

## 先讲主线（一句话）

**前 32 帧视频先过 encoder，predictor 再预测未来 1 秒（8 帧）特征，得到总计 40 帧对应的特征序列；这个序列作为 probe 输入，由 query 做聚合，最后输出 verb/noun/action 三个分类结果。**

---

## 1. 输入到底是什么

在 EK100 配置里，模型看到的是一段历史视频：

- 历史输入：`32` 帧（`frames_per_clip=32`，`fps=8`）
- 所以历史时长：`32 / 8 = 4` 秒

也就是：**先看过去 4 秒，再做未来动作预测**。

---

## 2. predictor 在预测什么

predictor 不是直接预测类别，而是预测**未来视频的 token 特征**。

在当前配置中：

- `anticipation_time_sec=[1.0, 1.0]`：目标是未来 `1` 秒
- `fps=8`：未来 1 秒对应 `8` 帧

因此可以直观理解为：

- encoder 给出前 32 帧的上下文特征
- predictor 基于上下文，预测未来 8 帧对应的特征（代码里以 token 形式实现）

---

## 3. probe 的输入是什么

probe 的输入不是原始像素，也不是单向量，而是**拼接后的时序特征序列**：

- 历史 32 帧特征（context）
- 未来 8 帧特征（predicted）

合起来就是：**40 帧 feature**（按 token 序列表达）。

这一步是整个逻辑最关键的地方：  
**probe 分类时，看的不是“仅过去”，而是“过去 + 预测到的未来”。**

---

## 4. probe 如何聚合（query 机制）

有了 40 帧对应的长 token 序列后，不能直接拿来分类，所以先做 attentive pooling。

它的做法是：

1. 定义几个可学习 query token
2. 让每个 query 去和整段 token 序列做 cross-attention
3. 每个 query 聚合出一个任务相关向量

在 EK100 中使用 3 个 query：

- query-1 聚合出 `verb` 向量
- query-2 聚合出 `noun` 向量
- query-3 聚合出 `action` 向量

这比“全局平均池化”更有针对性，因为三个任务关注的时空线索不完全一样。

---

## 5. 最终输出是什么

每个聚合向量接一个线性分类层，得到三组 logits：

- `verb logits`
- `noun logits`
- `action logits`

其中 `action` 是由 `(verb, noun)` 组合映射成的动作类。

训练时总损失是三项相加：

`L_total = L_verb + L_noun + L_action`

---

## 6. 为什么这个逻辑合理

这个头的核心思想是：

- **encoder** 负责“看懂过去 32 帧”
- **predictor** 负责“补出未来 1 秒（8 帧）特征”
- **probe** 在“32+8=40 帧特征”上做任务判别

所以它做的不是普通识别，而是“带未来推断信息的 anticipation 分类”，这和 EK100 的目标是对齐的。

---

- 主流程：`evals/action_anticipation_frozen/eval.py`
- 主干封装（32 帧输入 + 未来特征预测 + 拼接）：`evals/action_anticipation_frozen/modelcustom/vit_encoder_predictor_concat_ar.py`
- 额外头（query 聚合 + 三分类器）：`evals/action_anticipation_frozen/models.py`
- attentive pooler：`src/models/attentive_pooler.py`
- EK100 标签构建：`evals/action_anticipation_frozen/epickitchens.py`
